# Owly 仕様

この文書は、Owly の責務、設計思想、将来仕様を定義する。現在利用できるコマンドと設定は [CLI リファレンス](cli.md) と [設定リファレンス](configuration.md) を参照する。この文書の「必要な CLI コマンド」には、現行実装だけでなく将来候補も含まれる。

## 1. Owly の責務

Owly は、AI エージェントが育てる Markdown Wiki の「構造契約」と「構造の検証」を担う。

人間が Wiki の構成を定義し、エージェントがソースを読み、知識を既存ページへ統合し、Owly が構造上の正しさを検証する。この責務分担を崩さない。

### Owly が保証するもの

- `owly.yml` に明示されたディレクトリ、文書タイプ、フィールド、値の型、許可値、リンク規則
- frontmatter の構文と構造
- ページ ID、ページ間リンク、Graph の境界と入口
- ソースの存在、パス、ハッシュ、出典との対応
- 孤立ページ、到達不能ページ、壊れたリンクなど、構造から決定できる保守診断
- 同じ設定とファイルに対する再現可能な診断
- Markdown と設定を正本とする、再構築可能な検索インデックス

### Owly が保証しないもの

- 本文の意味、真偽、文体、文章品質
- 要約、分類、重複ページの統合、矛盾の意味的な解消
- 「この情報を覚えるべきか」という判断
- 自然言語の質問への回答や、引用付きの説明
- Git の履歴、レビュー、マージ、競合解消

これらはエージェント、人間、既存の検索・編集・Git ツールに任せる。Owly は知識の内容を理解したふりをしない。

### 当面の対象範囲

当面は、`raw/` に保存できる単一ソース、またはソース単位に分けて保存できる入力を対象とする。PDF、URL から取得した文書、画像、会話ログなどが該当する。

コードリポジトリのように、複数ファイルの関係や Git の履歴を前提に理解する必要があり、そのまま `raw/` に置けないファイル群は対象外とする。プロジェクト固有の知識をどこに保存し、どの差分を取り込むかは後で別途設計する。

## 2. 基本モデル

### 2.1 Wiki はコンパイル済み知識である

Wiki はソースを毎回検索して答えを生成する場所ではなく、ソースから抽出・整理された知識を蓄積する成果物である。新しいソースを取り込むときは、まず既存ページとの対応を調べ、既存ページを更新する。新しいページは既存ページに統合できない場合だけ作る。

この判断自体は意味理解を必要とするためエージェントが行う。Owly は、統合後のページが契約、リンク、出典の規則を満たすかを検証する。

### 2.2 正本と派生データを分ける

正本は Git で管理する Markdown、frontmatter、`owly.yml` である。検索用 SQLite、Graph のキャッシュ、統計、診断キャッシュは派生データであり、正本から削除・再構築できなければならない。

ソースを取り込んだ記録には、少なくとも次を持たせる。

- ソースのパスまたは識別子
- 取得時刻と更新時刻
- 内容のハッシュ
- 任意の出典 URL
- そのソースから生成・更新したページ

ソースからページへの対応は各ページの frontmatter を正本とする。ソースからページへの逆引き、ハッシュ比較、更新差分の検索は SQLite インデックスから行う。SQLite は正本から再構築できるため、別の必須台帳ファイルは持たない。

取り込み履歴や `last_commit_synced` のようなワークフロー固有の状態が必要な場合は、各 Agent Skill が任意のサイドカーへ保存してよい。ただし、その状態を Wiki の知識や Owly の構造契約の正本とはみなさない。

### 2.3 Graph は分割され、入口で接続される

Graph は無制限に一つへ膨らませない。各 Graph は一つの知識領域として内部を完結させ、Graph 間は相手の入口ページだけを参照する。

```text
Graph A ──→ Graph B の入口 ──→ Graph B の内部
```

Graph が別の Graph 群を参照できるようにし、必要な深さまで再帰的に構成できるようにする。個別記事への越境リンクは、構造上の検証エラーまたは明示的な例外とする。

### 2.4 書き込みは追跡可能で、検証は非破壊である

書き込みを行うスキルは、変更したページ、ソース、判断、時刻をログに残す。代表的な派生ファイルは次のとおりである。

- `entrance.md`: グラフの必須入口ページ
- `log.md`: 取り込み・更新・検証の時系列ログ
- `hot.md`: 次のセッションが最初に読む短い活動スナップショット

これらは正本ページを隠すための独自データベースではなく、エージェントの探索コストを下げる補助情報である。`entrance.md` は必須で、`log.md` と `hot.md` は必要な運用でだけ生成する。検証コマンドは、Markdown、設定、インデックス、ログを自動修正しない。

## 3. 必要な Agent Skills

スキルは自然言語の判断を担当するが、Owly のコア境界を越えて自動修正や意味の断定を行ってはならない。`using-wiki` は共通の入口・ルーターとし、ユーザーが直接呼ぶ第一級スキルとして `wiki-query` と `wiki-ingest` を提供する。それ以外は、第一級スキルから呼び出す専門スキルとする。

### 第一級スキル

#### `using-wiki`（共通入口）

すべての Wiki タスクの最初に使う。対象 Wiki と設定を解決し、設定・概要・検索・書き込み・保守のどの専門スキルが必要かを選ぶ。既存の `AGENTS.md` など所有者固有のルールがあれば先に読む。`wiki-query` と `wiki-ingest` はユーザーが直接呼び出してよいが、この解決手順と安全境界を共有する。

#### `wiki-query`

Wiki の構造化検索と本文検索を組み合わせ、出典となるページを示しながら自然言語の質問に答える。構造化検索は `wiki-search` に委譲し、本文検索は `rg` などを使う。回答の意味的正しさは Owly の検証対象ではなく、未検証の推測と出典に基づく記述を区別する。

#### `wiki-ingest`

Markdown、PDF、URL、画像、会話ログなど、`raw/` に保存できるソースを Wiki に取り込む。エージェントが内容を抽出・要約・分類し、既存ページとの統合を判断する。ソースのハッシュ、出典、生成ページをページの frontmatter に記録し、取り込み後に構造を検証する。Owly 自身が要約や真偽判定を行うコマンドは作らない。

### 専門スキル

#### `config-wiki`

人間との対話から `owly.yml` の構造契約を設計する。既存設定を読み、未指定の項目を保持し、書き込み前に差分と影響を確認する。設定作業の最後に設定自体と Wiki を検証する。

#### `wiki-overview`

検証する前に、ディレクトリ、文書タイプ、ページ数、Graph の入口、診断、ソースの状態を読み取り専用で把握する。これは「ルール違反を見つける」スキルではなく、「この Wiki が何で構成され、どこを調べるべきかを知る」ためのスキルである。ファイル名や記事の雰囲気から、未定義の構造を推測しない。

#### `wiki-search`

frontmatter、ページ ID、リンク、ソースを構造化検索する。本文の単語・フレーズ検索は `rg`、`fd`、`grep`、エディタへ委譲する。検索結果を意味のある回答に変換するのはエージェントの仕事であり、Owly の検索結果は根拠として追跡可能にする。

#### `wiki-validate` または検証ワークフロー

変更の前後で構造を検証する。エラー、警告、対象パス、診断コード、修正の根拠をエージェントが扱える JSON で取得し、検証失敗を成功として報告しない。検証は常に非破壊とする。

#### `wiki-maintenance`

検証結果、ソースの鮮度、更新履歴、Graph の形状を横断して、対応すべき保守候補を発見し、優先順位を付けて報告する。壊れたリンク、孤立・到達不能ページ、重複 ID、ソースの欠落・変更、インデックスとの不整合、Graph 境界違反に加え、古いページ、重複候補、リンク不足などを扱う。

`validate` は「契約に違反しているか」を決定論的に判定する検査であり、`maintenance` は「違反でなくても、継続運用上どこを直すべきか」を整理する調査である。`maintenance` は意味的な重複や内容の古さを断定せず、候補と根拠を示す。どちらも修正、移動、削除、アーカイブは明示的な承認後に行う。


## 4. 必要な CLI コマンド

以下はコマンドの論理仕様である。サブコマンド名は実装上変更してよいが、責務と安全性は維持する。

### 4.1 初期化と契約（現行実装）

| コマンド | 必要性 | 仕様 |
|---|---|---|
| `owly init --list-templates` | 必須 | Agent が選べるスターターテンプレートの名前と説明を出力する。ファイルは変更しない。 |
| `owly init --template <name>` | 必須 | 指定テンプレートから `owly.yml` と `entrance.md` を作る。既存の設定やページを上書きしない。 |
| `owly config validate` | 必須 | YAML、設定スキーマ、型、値、パス、Owly バージョン互換性を検証する。Wiki の内容には依存しない。 |
| `owly schema` | 必須 | エージェントが読める完全な契約を text/JSON で出力する。Wiki ルート、タイプ、必須・任意フィールド、許可値、例外を含む。 |

### 4.2 インデックスと構造

| コマンド | 必要性 | 仕様 |
|---|---|---|
| `owly index` | 必須 | Markdown と設定から SQLite の frontmatter・ページ・リンク・ソースインデックスを作成または更新する。正本は変更せず、再実行・再構築できる。 |
| `owly inspect` | 必須 | ディレクトリ、タイプ、ページ数、Graph の入口、ソース状態、インデックス状態を一つの JSON で取得する。人間向け表示も提供する。 |
| `owly search` | 必須 | `field:value` などの構造化条件を SQLite インデックスから検索する。本文全文検索、意味検索、自然言語回答は提供しない。 |
| `owly graph` | 現行 | ページ、リンク、Graph、入口、壊れた参照を JSON で標準出力へ出力する。インデックスや正本を変更しない。 |
| `owly graph export` | 将来候補 | 出力先や形式を選べる Graph エクスポート。現行バージョンには存在しない。 |
| `owly graph analyze` | 将来候補 | 孤立、到達不能、ハブ、境界違反、入口からの到達性を分析する。現行バージョンには存在しない。 |

`overview directories` と `overview types` のような複数コマンドは互換性のために残してよいが、仕様上は `inspect` のビューとして扱う。情報が重複し、入口スキルの手順を複雑にするだけの別コマンドは増やさない。

### 4.3 検証と保守

| コマンド | 必要性 | 仕様 |
|---|---|---|
| `owly validate` | 必須 | 設定、frontmatter、タイプ、フィールド、型、許可値、ID、リンク、Graph 境界、ソース参照、孤立ページを決定論的に検証する。 |
| `owly validate --file <path>` | 推奨 | 編集したページと関係する診断を高速に検証する。全体検証との差分を明示する。 |
| `owly check` | 将来候補 | CI 用の短い別名。現行バージョンには存在しない。 |
| `owly maintenance` | 将来候補 | 保守候補を検出・分類・JSON 出力する。現行バージョンには存在しない。 |

診断には安定したコード、重要度、パス、フィールド、説明、可能なら修正のヒントを含める。エラー時は非ゼロ終了し、JSON 出力と人間向け出力で判定を変えない。

### 4.4 出力と導入

| コマンド | 必要性 | 仕様 |
|---|---|---|
| `owly skill <directory>` | 必須 | `using-wiki` を入口として、必要な専門 Skill 一式を配置する。トップレベルに別の `owly` 入口 Skill は作らない。 |
| `owly onboard` | 任意 | エージェントへの導入手順を表示する。プロダクトの検証責務や安全境界を説明する。 |
| `owly export` | 将来候補 | Wiki や Graph を標準形式へ書き出す。現行バージョンには存在しない。 |

## 5. 明確に不要な機能

哲学に照らすと、次のものは Owly のコアコマンドとしては不要である。

- Markdown 本文の全文検索、置換、エディタ機能
- LLM を呼び出す要約、分類、自然言語 QA、意味検索
- ファイル名や既存ページからのスキーマ自動推測
- `validate` 実行時の自動修正、整形、リネーム、削除
- Wiki 専用の履歴・レビュー・同期機構による Git の代替
- 正本を隠す独自 DB やクラウドサービスへの依存
- Graph 全体を常に一つへ平坦化する機能
- 保守候補を人間の確認なしに統合・アーカイブする機能

また、単に現在の実装に存在するという理由だけで、`onboard`、複数の概要コマンド、Skill 配布用の補助コマンドをコア概念とみなしてはならない。それらは導入・互換性のための周辺機能である。

## 6. 標準ライフサイクル

```text
人間が owly.yml を定義
        ↓
using-wiki が対象と契約を解決
        ↓
エージェントがソースを ingest
        ↓
必要に応じて index・log・hot とページを更新
        ↓
Owly が index と Wiki の構造を validate
        ↓
人間またはエージェントが診断を確認して修正
        ↓
Git が差分・レビュー・履歴・復元を担う
```

このループで、エージェントには読解・要約・分類・執筆・リンク付けを任せられる。一方、正しさの契約を定義することと、構造違反を決定論的に検出することは Owly と人間の側に残る。

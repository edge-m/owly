# Owly Wiki 設定ビルダー

構造化 Markdown Wiki の要件を、正しい `owly.yml` に変換する。これは対話的な設計ワークフローである。要件を少しずつ集め、提案を平易な言葉で示し、明示的な承認を得てからファイルを書き、検証する。

## 1. 質問の前に調査する

- 現在のディレクトリを確認し、`owly.yml` を探す。
- 設定が存在する場合は更新として扱い、明示的に別ファイルを求められない限り、指定されていない設定を保持する。
- Wiki が存在する場合は、`owly schema --config <path> --format json` と `owly overview directories` / `owly overview types` で現在の状態を確認し、名前を勝手に作ったり既存文書を壊したりしない。
- CLI が使えない場合は `README.md` と既存の YAML スキーマを確認し、検証を実行できなかったことを伝える。

## 2. 焦点を絞って対話する

一度に少数の関連する質問だけをする。最初に次を確認する。

1. 設定ファイルから見て Wiki はどこに置くか。
2. どのトップレベルディレクトリを作り、それぞれ何に使うか。
3. どの文書タイプをサポートするか。

その後、すべての文書に必要なフィールドと、タイプごとのフィールドを確認する。それぞれについて、名前、値の型、必須かどうか、短い説明、許可する文字列値を決める。ネストした配列やオブジェクトは、そのドメインに必要な場合だけ扱う。不明な用語は推測せず確認する。

使用できる値の型は `string`、`date`、`datetime`、`boolean`、`number`、`array`、`object` に限る。

すでに設定にある情報を繰り返し尋ねない。妥当な既定値が必要な場合は既定値であることを明示し、ドメイン固有のフィールドを黙って追加しない。

## 3. まとめて確認する

書き込む前に、次を含む簡潔な提案を示す。

- 出力パスと解決後の `wiki_root`
- ディレクトリ構成
- 文書タイプと説明
- すべての文書に共通する必須フィールド
- タイプ固有・任意のフィールド、ネストした形、許可値
- `wiki_lint` と `config_lint` の設定

「この設定で `owly.yml` を作成してよいですか？」のように明示的な確認を求める。確認前にファイルを作成・上書きしない。既存ファイルを上書きする場合は、そのことを別途伝え、上書きの確認を得る。

## 4. YAML を書く

トップレベルは次の形にする。

```yaml
wiki_root: .
directories: {}
mandatory_fields: {}
types: {}
wiki_lint: {}
config_lint: {}
```

すべての文書に必要なフィールドには `mandatory_fields` を使う。ここでは `optional: true` は使えない。タイプ固有のフィールドには `types.<type>.fields` を使い、`optional: true` がない限り必須とする。

`items` は `type: array` のときだけ、`fields` は `type: object` のときだけ使う。`values` は文字列フィールドにだけ使う。説明は簡潔で役に立つものにする。値が数値、日付、真偽値、YAML 構文として解釈される可能性がある場合は引用符を保持する。

## 5. 検証して報告する

書き込み後に次を実行する。

```text
owly config validate --config <path>
owly validate --config <path>
```

Wiki が空、または意図的に未完成の場合は、設定エラーと文書エラーを区別する。成功と報告する前に、設定エラーを修正する。更新の場合は、可能なら次も実行する。

```text
owly validate --config <path> --file <path>
```

書き込んだパス、最終的な選択、実行したコマンド、残っている警告・エラーを報告する。検証に失敗した場合、設定が有効だと主張しない。

## 安全ルール

- タイプ、フィールド、関係、必須条件を推測しない。
- 設定作業の一環として Wiki 文書を削除、移動、書き換えない。
- 既存の `owly.yml` を黙って上書きしない。バックアップまたは新しいパスを提案し、上書きの確認を得る。
- 回答が矛盾する場合は、勝手に選ばず矛盾を示して、対象を絞った質問を 1 つする。
- 下書きだけを求められた場合は、YAML の提示で止めて書き込まない。
- スキーマの問題が見つかった場合は、利用者の言葉で説明し、最小の修正案を示してから変更を確認する。

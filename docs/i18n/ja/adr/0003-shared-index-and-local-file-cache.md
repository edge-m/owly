# ADR 0003: 共有インデックスDBとローカルファイルキャッシュを分離する

- 状態: 採用
- 日付: 2026-08-30

## 文脈

Owly には、Wiki の構造を検索するための SQLite インデックスと、ファイルを毎回読み込んで解析するコストを抑えるためのキャッシュが必要になる。

この2つは性質が異なる。

- SQLite インデックスは、Git で管理し、複数ユーザー間で共有する
- ファイル読み込みキャッシュは、ユーザーごとの実行環境に閉じ、Git では管理しない

ファイル読み込みキャッシュに SQLite を使う案もあるが、保持する情報はファイルのパス・更新時刻・サイズだけであり、複雑な検索や部分更新は必要ない。

## 決定

共有インデックスDBとローカルファイルキャッシュを別物として扱う。

### 共有インデックスDB

- Wiki の検索用インデックスを保持する
- Git 管理の対象とする
- Frontmatter、リンク、参照元、文書ハッシュなどを保持する
- DB ファイル自体の変更確認には `mtime` とサイズを使う

### ローカルファイルキャッシュ

- Gitignore 対象とする
- 平文の compact JSON とする
- Wiki のディレクトリごとに1ファイルを持つ
- 対象ファイルごとに、次の3値だけを保持する

```text
path
mtime
size
```

- SQLite のインデックス内容やFrontmatterの解析結果は重複して保持しない
- DBの `mtime` とサイズは、ローカルキャッシュ全体のメタデータとして保持する
- DBまたはファイルのメタデータが一致する場合、SQLiteのインデックスを再利用する
- 一致しない場合、対象ファイルを読み込み直して解析する

キャッシュは正しさの根拠ではなく、再生成可能な高速化データとして扱う。キャッシュが壊れている場合は削除して再構築できるようにする。

### ディレクトリあたりのファイル数

1ディレクトリに含まれる処理対象Markdownファイル数が250を超えた場合、ディレクトリ分割を推奨するwarningを出す。

- 250は推奨上限であり、処理を失敗させる制限ではない
- 除外設定を適用した後の処理対象ファイル数を数える
- warningはディレクトリ単位で報告する

## 理由

- 共有DBにユーザー固有のファイル時刻を混ぜずに済む
- Git管理されるデータと、一時的な実行環境依存データの責務が明確になる
- パス・mtime・サイズだけなら、SQLiteよりJSONのほうが実装・依存・デバッグのコストが小さい
- ディレクトリ単位なら、プロジェクト全体を1ファイルに集約するよりメモリと書き換え範囲を抑えられる
- ファイル単位に分割するより、小さなファイルの大量生成やファイルシステム上の管理コストを避けられる
- 250ファイルを目安にすることで、キャッシュファイルの大きさと並列処理の粒度を一定範囲に保てる

## 制約と受け入れるリスク

`mtime` とサイズが同じまま内容だけが変わった場合、変更を検出できない可能性がある。これはキャッシュを高速化ヒントとして扱う前提で受け入れる。

完全な内容同一性が必要になった場合は、対象ファイルのハッシュ確認または再解析へ進む拡張を検討する。

JSON の更新は、一時ファイルへ書き込んでから rename する原子的な置換とする。
